## 3 本轮暴露并修复的问题

### 3.1 重复音频被错误去重

第一轮 90 分钟测试在早期观察到 2020 个音频块、404 个持久窗口，却只有 4 个 ASR 完成

原因是 ASR 幂等键只使用音频内容哈希，可重复测试音频在再次出现时被当成同一个任务

修复后，幂等键同时包含会话、来源、采集时间和内容哈希，相同音频在不同时间产生不同任务，同一时间点的真实重传仍保持幂等

该轮结果无效并保留为失败证据，没有计入长测通过

### 3.2 单一 LLM 通道阻塞翻译

修复 ASR 幂等键后的第一轮 30 分钟运行收到 1783／1783 个 ACK，产生 357 条字幕、357 条译文和 70 张讲解卡，重复字幕与 OOM 都为 0

应用层推理耗时通过，但数据库报告发现：

| 指标 | 结果 | 门禁 |
|---|---:|---:|
| Worker 领取 p95 | 10.553 秒 | 2 秒 |
| ASR 端到端 p95 | 2.996 秒 | 3 秒 |
| 翻译端到端 p95 | 14.323 秒 | 8 秒 |
| 讲解端到端 p95 | 32.671 秒 | 20 秒 |

原因是翻译和长讲解共享同一领取通道，讲解执行期间新翻译只能排队

该轮没有计入通过

### 3.3 7B 单并发仍会持续排队

把 ASR、翻译和讲解拆成独立领取通道并切换到 7B 后，5 分钟预检通过

后续 30 分钟重跑在约 17 分钟时发现 Ollama 仍按单并发处理真实长讲解，翻译端到端 p95 上升到 13.698 秒

该轮被提前停止并正常释放录音租约，没有用剩余时间掩盖失败趋势

最终修订把 Ollama 设为双并发，并保留独立 ASR、翻译和讲解通道

## 5 项目、多设备与租约

自动验证范围：

- 不同 Authentik UID 不能读取彼此项目
- 项目列表不能隐式认领历史会话
- 同一用户的两个设备得到相同项目和时间线
- 同一项目只有一个设备取得有效录音租约
- 第二个设备得到明确的 `409 recording_lease_conflict`
- 45 秒内原设备可恢复，过期后新设备接管并递增 generation
- 长于 45 秒的断网若没有设备接管，原设备仍可原地续回并补传缓存
- 旧租约和旧 generation 不能继续上传
- 录音租约的服务端令牌摘要不会出现在续期响应、项目更新或普通日志
- SSE 使用 `Last-Event-ID` 补齐更新且不重复
- 停止后观察设备同步得到录音停止和模型处理状态

## 6 音频恢复

自动验证范围：

- ACK 只在音频对象和 SQLite 同时提交后返回
- 重复发送相同帧只保留一个提交结果
- 同序号但不同内容的重传被拒绝
- 第 2 帧先到时装配器等待第 1 帧
- 第 1 帧补到后形成一个连续窗口
- Core 在未满窗口和完整窗口入队后重启均能继续装配
- 停止时从持久块封存尾部
- 浏览器刷新时恢复 IndexedDB 未确认帧
- 所有 ACK 完成后再次刷新不会重新使用序号 1

## 7 ReadWeave

真实 ETAPI 验证范围：

- 项目和会话目录可以幂等创建
- 稳定字幕、翻译、讲解和材料证据进入各自笔记
- 讲解以背景补充、生僻词、疑似 ASR 错误、复习问题和证据形式呈现，不写入原始 JSON
- 每次修改前创建 revision
- 标记外人工内容保持不变
- `99 我的笔记` 保持不变
- 管理标记缺失时源笔记不被覆盖，并创建一个恢复笔记
- ReadWeave 离线时任务保留，恢复后自动补写
- 后续成功校对会清除当前冲突状态，但不删除历史更新记录

浏览器从未取得 ETAPI Token，默认投影不包含原始音频、原始课件或临时下载地址

## 10 2026-08-29 恢复修订与第二轮长测

### 10.1 第一轮 90 分钟失败证据

第一轮浏览器运行完成约 90 分钟采集，但末段 SSH 转发静默断开

浏览器继续把未确认音频保存在 IndexedDB，证明本地保护有效，但连接恢复后客户端一次发送全部待确认帧，WebSocket 再次停滞，会话无法在停止等待时间内完成

该轮没有计入通过

修订内容：

- SSH 转发增加 15 秒 keepalive、3 次失效退出和 1 秒监督重连
- 浏览器同时检查本地采集序号和服务器 ACK 进度
- 每条 WebSocket 最多保持 8 个音频帧在途，ACK 后再发送下一帧
- 连接关闭后清空在途标记，从 IndexedDB 中按原序号重新领取

### 10.4 当前模型组合

当前生产验证组合为：

- ASR：`faster-whisper:base@cpu`，`int8`，12 个线程
- 翻译与讲解：`ollama:qwen2.5:3b-instruct@cuda`
- Windows 模型 Worker：`AboveNormal` 调度优先级
- Agent 启动：ASR、Ollama、ASR 三段预热后才领取任务

8 秒私有合成窗口的 base CPU 基准中，12 个线程 p95 为 0.519 秒，是 4、8、12、16 和 24 线程对比中的最低值

### 10.5 第二轮 90 分钟判定规则

第二轮运行主动包含 Core 重启、GPU Agent 重启、Worker Gateway 中断和 ReadWeave 离线

运行早段同时出现用户程序和另一项仓库历史扫描的高 CPU 占用，导致累计 ASR 延迟超标，因此本轮只用于判定长时数据完整性、恢复和资源趋势，不能用于判定性能通过

提高 Worker 调度优先级后，最近任务恢复到冻结门禁以内，但仍会另跑一轮无干扰 30 分钟性能测试，不能用最近窗口替代整轮累计 p95
